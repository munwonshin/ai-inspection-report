# 원본 PDF 전체 인식 검증 · 0.3.8

검사일: 2026-10-22. 사용자의 요청에 따라 일반현황 인식을 원본 PDF 전체 직접 입력으로 변경했다. 사용 중인 실제 업무 PDF는 제공받아 시험하지 않았고, 원본 업무 자료를 API에 보내지 않았다. 모든 실제 AI 시험은 명확한 가상 자료다.

이전 방식은 AI가 찾은 값도 로컬 추출 텍스트에서 인용문이 연속해서 발견되지 않으면 버렸다. 표의 셀 순서·삽입 문장부호·스캔 페이지에서는 정보가 있어도 빠질 수 있었다. 새 방식은 원본 파일 전체를 input_file로 보내며, 로컬 인용 일치를 수락 조건으로 쓰지 않는다. 값/인용문 일치, 원본 물리적 쪽수 범위, 응답 스키마와 요청한 5개 항목을 검사한다. 시각적 근거는 AI가 제시한 것이며 독립 검증이 아니므로 사용자가 원본과 대조한다.

| 실제 가상 PDF 시험 | 원본 쪽 | 자동 입력 | AI 근거 쪽 | 기존 연속 인용 일치 | 입력/출력 토큰 |
|---|---:|---:|---:|---:|---:|
| digital | 3 | 5 | 2 | 0 | 2042/322 |
| scan | 3 | 5 | 2 | 0 | 3831/236 |

- 두 가상 문서는 3쪽이며 2쪽에 표가 있다. 하나는 문자 저장 순서와 시각적 셀 연결이 다른 표이고, 다른 하나는 2쪽 전체가 이미지여서 로컬 텍스트에 값이 없다. 렌더링한 두 표의 줄맞춤·가독성도 확인했다.
- 실제 앱의 PDF 읽기→실제 API→실제 Tk 위젯 경로에서 두 문서 모두 5개 값과 근거 2쪽을 확인했다. 전송 직전 base64를 복원해 원본 파일과 모든 바이트가 같은지 검사했다. 앞/뒤 페이지도 포함됐으며 별도 입력 텍스트 중복은 없었다.
- 새 AI 응답의 인용문은 두 경우 모두 기존 연속 문자열 검사와 0개 일치했다. 스캔형은 5개 값 자체도 로컬 텍스트에 없었다. 이 상태에서 새 방식은 5개를 채웠다. 실제 업무 파일의 실패 원인을 확정한 시험과는 구분한다.
- 방문 관련 4개 항목은 빈칸으로 유지됐고 초안 생성·HWP 저장 함수는 호출되지 않았다. 요청별 시간은 문서·캐시·네트워크에 영향을 받으므로 일반 속도나 업무 10분 달성으로 해석하지 않는다.
- 단위 검사 45개 통과. 원본 전량 전송, 중복 텍스트 없음, 스캔 근거 수락, 쪽수/인용문/출처 오류 배제, 미인식 이유, 잘못된 응답 거부와 기존 승인 경계를 포함한다.
- Tk 일반현황 7시나리오, 기본/최소 창·배율·편집·일반현황 32가지 배치, TkDND 첨부/삭제 및 모의 스트리밍 검사를 통과했다. 근거 보기→직접 수정 시 근거 해제, PDF 해제 시 원본 메모리 제거도 확인했다. 탐색기→새 frozen EXE 드래그를 직접 반복했다고 주장하지 않는다.
- 빌드 EXE의 Python 코드가 최종 소스와 일치함을 확인했다. 실제 HWP 저장/재열기·실물 NAS·다른 PC 시험은 이번 버전에서 반복하지 않았다. HWP/core/API/vault/streaming/PDF 처리 코드는 0.3.7과 동일하다.

원본 전체 전송·추가 과금은 메인 화면과 API 설정 및 사용 안내에 표시했다. API store=False, Windows 키 저장소, 수동 입력 보존, 결과 승인 후에만 저장하는 원칙을 유지했다. 모델의 모든 업무 자료 인식 정확도나 3시간→10분 단축을 보장하는 시험은 아니다.
